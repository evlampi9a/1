# Разбор падения дневной выручки

Цель — за один проход ответить: **упал спрос или сломалась оплата**, когда именно, где (провайдер / продукт / сегмент) и сколько денег это стоило. Не останавливайся на первой гипотезе: каждая цифра потерь должна сходиться с общей дельтой дня.

## Источник данных

- Коннектор: `mcp__Amplitude_US__*` (org `zencreator`). Схемы инструментов загружай через ToolSearch.
- Проект: **Production, projectId `717020`**.
- Таймзона: **`Asia/Tel_Aviv`** — так считает основной график команды «Revenue» (chart `xu5xs22x`). Всегда передавай её в `date_range.timezone`, иначе цифры не совпадут с тем, что видит пользователь.
- Выручка: событие `Payment Succeeded`, `measured_as: property_sum`, свойство `$revenue` **обязательно** в `group_by` самого события:
  `{"event":"Payment Succeeded","group_by":[{"property":"$revenue","scope":"event"}]}`

Ключевые события и свойства:

| Что | Событие / свойство |
|---|---|
| Видел оффер (спрос) | `Payment Offer Viewed` (uniques) |
| Нажал «купить» (фронт) | `Payment Started` |
| Ушёл на форму провайдера (бэк) | `Checkout Started` (есть `billing`) |
| Успех / ошибка / брошен | `Payment Succeeded` / `Payment Failed` / `Payment Not Finished` |
| Провайдер | `billing` (stripe, voltpay, rounders, rounders_apple_pay, palwallet, …) |
| Платформа | `platformType` (zencreator, openmov) |
| Причина ошибки | `failureMessage` на `Payment Failed` |
| Новый/повторный | `isFirstPayment` (значения `true`/`True`) |
| Оффер / купон | `isOfferPurchase`, `coupon` |

## Порядок анализа

Сначала посчитай эпохи границ дня в Тель-Авиве (`date -d '2026-10-20T21:00:00Z' +%s` = начало 21.10 IDT; зимой смещение +2, летом +3). **После каждого запроса проверяй `xValuesForTimeSeries`** — при абсолютных датах Amplitude иногда сдвигает окно на день, не путай индексы.

### 1. Масштаб: с чем сравниваем
Один запрос, 60 дней, `interval: day`, формула `PROPSUM(A); TOTALS(B); UNIQUES(C)` (выручка, платежи, плательщики) по `Payment Succeeded`.
- Сравни день D с **D-1, D-2, D-7** и средним за 6 предыдущих дней.
- Посчитай недельные суммы (7 дней до D включительно против предыдущих 7).
- Разложи: выручка = плательщики × платежей на плательщика × средний чек. Что из трёх упало?
- Если D-7 такой же низкий и неделя к неделе ровная — прямо скажи, что «падения» к прошлой неделе нет.

### 2. Когда: часы
`interval: hour`, максимум 7 дней. Выручка и число успехов по часам за D, D-1, D-2 (и D-7 отдельным запросом, если нужно). Сверни в блоки 00–06 / 06–12 / 12–18 / 18–24 и найди окно, где потеряны деньги. Считай в Python (Bash), не в уме.

### 3. Спрос или оплата: воронка
За D, D-1, D-2 (дневно и по часам в проблемном окне): uniques `Payment Offer Viewed`, totals `Payment Started`, `Checkout Started`, `Payment Succeeded`, `Payment Failed`, `Payment Not Finished`.
- **Started на месте, а Succeeded ниже и Failed/Not Finished выше** → проблема в оплате, иди в шаг 4.
- **Падают Offer Viewed / Started** → проблема спроса, иди в шаг 6.
- Конверсия окна = Succeeded / Started; норма ~58–65%.

### 4. Где сломалось: провайдеры
По `billing` за D, D-1, D-2, `groupByLimit: 20`:
- выручка (property_sum), Succeeded totals, Failed totals, **Checkout Started totals**;
- конверсия провайдера = Succeeded / Checkout Started;
- **ищи новых провайдеров** (0 в предыдущие дни, >0 в D) и провайдеров с нулём успехов — так находились cardflo (20% конверсии в день запуска) и payok (0 успехов);
- для подозрительных — почасово Succeeded/Failed/Checkout в проблемном окне;
- `failureMessage` по дням для проверки причины.

Сложи дельты выручки провайдеров к среднему D-1/D-2 — сумма должна примерно сойтись с общей дельтой дня.

### 5. Какие продукты пострадали
Выручку по бакетам чека через фильтры на `$revenue` (а не через `price`!): `<30`, `30–90`, `90–300`, `300+`, формулой `PROPSUM(A); PROPSUM(B); PROPSUM(C); PROPSUM(D)`.

### 6. Если упал спрос (тренд, а не авария)
- Новые vs повторные: `isFirstPayment` = true / is not true.
- Крупные чеки: Payment Started uniques с `price ≥ 90` и `$revenue ≥ 300` по неделям.
- `platformType`, офферы/купоны (`isOfferPurchase`, `coupon`).
- Верх воронки: uniques `Registration Completed`, `_active`.
- Микс провайдеров по неделям (включения/отключения провайдеров дают всплески и провалы).

## Подводные камни (уже наступали)

- `interval: month`/`week` расширяет окно до целых календарных периодов — для сравнения двух недель используй абсолютные даты и `interval: day`, суммируй сам.
- `formula_labels` нельзя вместе с `group_by` — получишь ошибку компиляции.
- Две группировки внутри события (`creditsCount` + `$revenue`) суммируют не то — используй chart-level `group_by` и `$revenue` в event-level.
- `price` содержит FX-конвертированные значения (19.03…19.09, 49.26…49.42, 96.2…96.6), которые меняются каждый день и вылетают из top-N. Для продуктов используй бакеты по `$revenue`.
- Ошибки «Payment expired after 24h pending» приходят **на следующий день** — не приписывай их дню, в который они записаны.
- `data_table` с `columns[].event` строкой не принимается — проще делать segmentation.
- `gp:is_paying` почти пустой — не сегментируй по нему.
- Hourly на 8 дней не работает (лимит 7).

## Формат ответа

1. В чате — подробный разбор с таблицами: сравнение D / D-1 / D-2 / D-7, окно по часам, воронка, провайдеры с суммой потерь, вывод «спрос vs оплата», что делать.
2. Затем предложи короткую справку для Slack по шаблону:

```
**Revenue <дата> — $<X>k: в чём причина**

**Коротко:** <одно предложение: спрос/оплата, что сломалось>.

**Сравнение**
• Против <D-1>/<D-2> ($…k / $…k): **−$…k**
• Против <D-7> ($…k): …; неделя к неделе: $…k против $…k

**Когда:** <окно по Тель-Авиву>, конверсия в оплату …% против …%.

**Где сломалось**
• <провайдер/сегмент>: <факт> → ≈ −$…k
• …

**Что сделать**
1. …
2. …

_Источник: Amplitude (Production), время по Тель-Авиву_
```

Пиши по-русски, суммы в $k с одним знаком после точки, время — по Тель-Авиву. Гипотезы, которые нельзя подтвердить данными, помечай как гипотезы.
