## Что агент делает, по шагам

### 1. Готовит папку

`../<дата среды>-review/` — например `2026-09-09-review/`. Внутри: `data/` для сырья,
`raw/` для JSON-выгрузок. Скрипты `ex.py`, `agg2.py` копируются из предыдущей папки.

### 2. Собирает базовые ряды

Проект Production `717020`, tz `Asia/Tel_Aviv`, данные **по воскресенье включительно**;
текущая неделя неполная, в сравнения не идёт. Окна: последняя полная неделя против предыдущей,
плюс месяц к месяцу. Сырьё сохранять в файлы — по ним потом валидируют.

#### Как считаются ряды (добавлено 20.10.2026)

**Генерации, доля failed.** `Task Status Changed`, разрез по `status`:
`failed / (completed + failed + partial)`. Знаменатель — завершившиеся задачи, не `Task Created`:
иначе в него попадают задачи, которые ещё идут.

**Почему failed — по `errorCategory`** (свойство на `Task Status Changed`). Приходит с 15.10,
заполнено полностью с 16.10 — раньше 16.10 причины не раскладываем, только общий failed.
В трекинг-плане свойства нет (статус unexpected), поэтому сумма групп каждый раз обязана сойтись
с общим failed — если не сошлась, свойство пропало или пришло не на всех событиях.

| Группа | Значения `errorCategory` | Что это |
|---|---|---|
| Наша модерация | `moderation_blocked`, `nsfw_detected` | продукт сработал как задумано |
| Модерация провайдера | `provider_policy_output`, `provider_content_policy`, `provider_policy_input` | отказ модели по контенту |
| Ошибка входа | `invalid_input` | неверный запрос/файл |
| Технические | `unknown`, `infrastructure`, `provider_timeout`, `deadline_exceeded`, `provider_rate_limit` | настоящие падения |

- **Аварией считаются только технические.** Модерация — не сбой: в «Срочное» её не выносим и как
  поломку не подаём. Ориентир 16–19.10: failed 10,88% задач, из них модерация (наша + провайдера)
  95,4%, вход 2,3%, технические 0,25% от всех задач.
- **Каждую группу показываем как % от всех задач**, а не как долю внутри failed — так видно,
  сколько задач теряет пользователь. Разрез по `toolType` и провайдерам — той же формулой.

**Регистрации по каналам.** Traffic Sources передаётся только canonical-именем
`d070d5a2-efec-4bef-9565-40bab615bcc3`, scope `derivedV2` (display name не принимается).
Сумма каналов обязана сойтись с тоталом `Registration Completed`. Падение раскладываем
по каналам и пишем, какой канал дал какую долю.

**Воронка mobile/web** (визит → оффер → старт оплаты → первая оплата): уникальные, окно 1 день,
mobile = device Android или iOS. Возле цифры всегда писать окно и определение mobile, иначе
кратность читают как недельную конверсию.

**Кредиты.** Продано = `PROPSUM(creditsCount)` по `Payment Succeeded`, потрачено =
`PROPSUM(credits)` по `Task Created`. Остаток пользователя = куплено − потрачено.
`gp:credits` за текущий остаток не брать: user property записан в момент события.

**Ловушки запросов.**
- `interval: week` и `month` расширяют окно до целых календарных недель/месяцев. Окно короче
  недели (например, 16–19.10) — только `interval: day` и сумма по дням.
- `chartId` перебивает `date_range`: даты берутся из сохранённого чарта. Для своих окон —
  ad-hoc определение.
- **`performed` (поведенческий фильтр «делал событие в окне») с `time_type: absolute` берёт
  локальные сутки Tel Aviv и включает сутки, в которые попал конец окна.** С UTC-эпохами W41
  превращается в 05–12.10. Для `performed` задавать эпохи локальной полуночи (UTC-эпоха − 10 800 с
  в октябре: W41 = 1791147600–1791752399). Для `date_range` графика UTC-эпохи правильные.
  Найдено 20.10.2026: так был сдвинут раздел «ушли / пришли» в разборе китов W41.

### 3. Проходит ВСЕ дашборды параллельными агентами

Список брать из Amplitude (`search_amp_entities`, `entityTypes: ["DASHBOARD"]`), **не из прошлого
отчёта**: дашборды заводят и переименовывают. На 01.09.2026 их 20.

По одному-два дашборда на агента. Каждому агенту давать:
- правила из `../CLAUDE.md`;
- окна сравнения;
- **список того, что уже есть в отчёте прошлой недели** — чтобы возвращали находки, а не пересказ;
- три ловушки: проект смешивает zencreator и openmov (проверять `platformType`); с 17.08 идёт
  закупной трафик PropellerAds на openmov (метрики со знаменателем «все пользователи» испорчены);
  сравнивать периоды средними за день, а не выбранными точками;
- жёсткий формат ответа: **находка → числа с окном → конкретное действие с ролью → подтверждено
  или гипотеза**. Максимум 5 находок. Если нового нет — честное «ничего нового».

Свод находок класть в `data/sweep-<дата>.md`.

### 4. Проверяет то, на чём стоят действия

Каждую цифру, из которой следует action item, пересчитать **вторым независимым запросом**.
Проверить полноту: суммы разбивок обязаны сходиться с тоталами (в том числе группы
`errorCategory` с общим failed и каналы с тоталом регистраций). Прогнать таблицу стоп-сигналов
из `../CLAUDE.md`.

### 5. Пишет два документа

- `ZenCreator_Product_Review_<дата>.md` — полный, со всеми разрезами и разделом «свип».
- `Statistics_Meeting_<дата>.md` — короткий, на 30 минут.

**Обязательные разделы короткой версии:**
1. Срочное, если есть работающая авария. Рост failed за счёт модерации — не авария (см. шаг 2).
2. «Где мы» — таблица KPI неделя к неделе.
3. Блоки по темам, каждый с бюджетом времени; сумма ≤ 30 минут.
4. **Статус действий прошлой недели** — что сделано, что нет, чем подтверждается.
5. **Список действий в конце**, разбитый на «сегодня / на этой неделе / до следующей встречи»,
   у каждого пустые поля «кто» и «срок» под заполнение на встрече.

**Обязательные разделы полной версии:** поправки к собственным выводам прошлой недели —
и ошибку, и поправку, с датой и причиной. Историю не переписывать.

**Оформление таблиц (добавлено 20.10.2026): одна цифра — одна ячейка.** Сравнение периодов
не пишется в одну ячейку через стрелку («2 283 → 2 234», «57,3 → 57,9%»): так таблица
не читается. Каждому периоду своя колонка («Стартов W41 | Стартов W42 | Конв. W41 | Конв. W42»),
при необходимости отдельная колонка «Δ». Цепочка из трёх периодов — три колонки. Так же нельзя
собирать несколько метрик в одну ячейку через «/» («404 933 / 295 675»): каждой метрике своя
строка. Стрелки и «/» между числами допустимы только в тексте, не в ячейках таблиц. Правило касается и Notion, и артефактов,
и слайдов.

### 6. Валидирует у Codex

По правилу от 20.08.2026: `orca orchestration run-create` → `task-create` со спекой валидации
→ `worker-start --agent codex` → дождаться → свести расхождения. Спека валидации минимум:
пересчёт производных чисел из сырья, стоп-сигналы, проверка полноты, отдельная проверка всего,
на чём стоит действие. Результат — в `data/validation-codex-<дата>.md`.

### 8. ОСТАНАВЛИВАЕТСЯ И ЖДЁТ

**В Slack ничего не отправлять самостоятельно.** Порядок такой:
агент готовит → показывает Леониду → Леонид читает и правит → вместе валидируем →

Формат сообщения: одна ссылка на артефакт плюс 5–6 пунктов с ключевыми числами, чтобы был смысл
без клика. Плюс строка, что комментарии удобнее оставлять прямо на странице и лучше до встречи.

### 9. Напоминает про приватность

Артефакт на время встречи делается публичным. **После встречи вернуть его в приватный режим** —
ставить строку в `~/Projects/tasks/INBOX.md`. Забирать доступ агент не умеет, это делает Леонид
через меню share на самой странице.

## Что важно не потерять

- **Отрицательный результат — тоже результат.** «Проверили, ничего не изменилось» экономит время.
- **Отделять подтверждённое от выведенного.** Гипотезу называть гипотезой.
- **Не бояться поправить самого себя.** В отчёте 02.09 таких поправок было четыре, и три из них
  нашёл Леонид или агенты свипа. Это норма, а не провал.
- **Число оценивающих рядом с долями оценок** — иначе таблица качества показывает поведение
  десятка людей, а читается как качество продукта.
